## 2025-07-29 - [Clean Object Reconstruction to Block Prototype/Property Pollution]
**Vulnerability:** Loading un-sanitized parsed JSON files from localStorage using the object spread operator (`...v`) or recursive merge allows attackers or hand-edited saves to pollute the prototype or inject unexpected keys directly into runtime data structures, which can trigger undefined behaviour, property pollution, or path/directory traversal via manipulative `level` strings.
**Learning:** Reconstructing the loaded data structure field-by-field with validated primitive types and strictly constructed sub-objects is a powerful, highly resilient defense-in-depth pattern. It avoids any exposure to unexpected fields and prototype/property pollution vectors entirely.
**Prevention:** Strictly limit string lengths, validate level name format using precise regular expressions (e.g., `/^[a-zA-Z0-9_-]+$/`), and explicitly construct newly validated return structures instead of spreading parsed JSON directly.

## 2025-08-11 - [Safeguarding localStorage Sub-State Validation and Object Prototype Injection]
**Vulnerability:** While parent save games were sanitized, sub-state validators like `isJournalState` and `isExploredState` lacked bounds and pattern checking, leaving the application vulnerable to Denial of Service (DoS) from bloated states or character injection. Additionally, helper parsed configurations (like settings) were queried directly, allowing inherited properties on `Object.prototype` to override application-level defaults.
**Learning:** Checking prototype keys (`__proto__`, `constructor`) inside validators and using `Object.prototype.hasOwnProperty.call` ensures properties are queried only from the object's own direct fields. A key challenge was that JS object literals `{ "__proto__": "value" }` modify the object's internal prototype instead of creating an own property, which prevents serialization. This requires the use of `Object.defineProperty` with `enumerable: true` during testing to correctly emulate a JSON-parsed payload with an own `"__proto__"` key.
**Prevention:** Enforce strict size/length bounds, sanitize keys against exact alphanumeric patterns, reject prototype properties explicitly, and retrieve properties using `hasOwnProperty` to completely bypass prototype pollution access vectors.

## 2025-08-25 - [Securing Reconstructed Sub-State Dictionaries against Prototype and Property Pollution]
**Vulnerability:** Dynamic key-value mappings (such as `explored` level-to-mask maps) and nested configuration states (like `objectives` and `journal`) were vulnerable to prototype/property pollution or constructor injection. In particular, looping over key-value pairs of raw objects and directly writing key-value assignments to a newly created plain object (e.g., `clean[lvl] = mask`) would modify the internal prototype if the key was `"__proto__"`, or inject arbitrary properties if the key was `"constructor"`. Additionally, validating/sanitizing properties without `hasOwnProperty` allowed lookups to fall back to `Object.prototype`.
**Learning:** When reconstructing dictionary objects or sub-states from JSON data, we must explicitly check for and skip `"__proto__"` and `"constructor"` keys in dynamic copy/reconstruction loops (e.g., in `sanitizeExplored`). Furthermore, querying properties in nested validators and deserializers (such as `isJournalState` or `sanitizeObjectives`) must be explicitly wrapped in `Object.prototype.hasOwnProperty.call` checks to prevent falling back to inherited global properties.
**Prevention:** Never perform dynamic assignments on reconstructed objects without explicitly blocking prototype injection keys (`"__proto__"`, `"constructor"`). Always enforce strict own-property queries via `hasOwnProperty` for validated properties.

## 2026-08-17 - [Raw Control Characters in Source Defeat the Audit Tools Themselves]
**Vulnerability:** `circuitKey()` in `src/systems/PowerGrid.ts` used a literal NUL byte as a composite-key separator, written as a raw `0x00` in the file rather than as an escape. The separator choice was correct and well-reasoned — NUL cannot collide with an editor-authored level name or tile-def ref — but the encoding made `src/systems/PowerGrid.ts` and `src/systems/GameState.test.ts` register as *binary* to the standard toolchain. `git diff` refused to show their contents, and `grep` **silently skipped them**: a repo-wide search returned a clean result set that simply omitted those files, with no warning, no error, and no indication anything had been excluded. A security or health audit run with grep would conclude the files were fine because it never read them.
**Learning:** A tool that silently returns *fewer* results is far more dangerous than one that errors, because a clean result reads as a passed check. Any raw byte below 0x09 in a text file triggers this class of blind spot across git, grep, ripgrep and most editors. The same audit surfaced a second silent-truncation bug in `tools/typeref/generate.ts`, where flattening a declaration to one line without stripping `//` comments commented out the remainder of the emitted snippet — output that still parsed as valid TypeScript while having quietly lost its tail. Both failures share a shape: the artifact looks well-formed, so nothing prompts you to look closer.
**Prevention:** Never write a raw control character into a source file; use the escape (`\u0000`), which is byte-identical at runtime and keeps the file plain text. When auditing, verify the tool actually read what you think it read — `git ls-files | xargs file` will expose any tracked text file reporting as `data`. Treat "the search found nothing" as a claim requiring evidence, not as a result.
