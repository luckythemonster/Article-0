## 2024-07-28 - [Accessible Listbox Navigation and Deferred Modal Focus]
**Learning:** In highly customized game DOM overlays, standard browser focus-management is often bypassed in favor of outer-panel key delegation. For screen readers, this renders listboxes silent unless they have `tabIndex="0"` and an active `aria-activedescendant` pointing to the selected option ID. Additionally, programmatic focus to modal panels should be deferred with `requestAnimationFrame` to ensure the elements are fully connected and laid out in the DOM before focus is requested.
**Action:** Always make custom listboxes focusable and track active descendants using unique option IDs. Defer programmatic modal focus calls using `requestAnimationFrame`.

## 2025-02-18 - [Guard Against Semantic Role Overwrites in DOM Overlays]
**Learning:** Generic click/keyboard helper utilities (like `asButton`) that stamp generic interactive attributes (like `role="button"`) can silently overwrite specific, semantic ARIA roles (like `role="tab"`) defined earlier on the element. In composite widgets like `role="tablist"`, this breaks parent-child ARIA associations and stops screen readers from announcing correct tab group contexts. Additionally, when using roving tabindex, programmatic focus must be shifted to the newly selected item on keypress to prevent leaving browser focus stuck on inactive tabIndex="-1" elements.
**Action:** Implement interactive event handlers directly or modify helper utilities to accept custom roles. Always check and restore focus to the newly activated roving tabindex node during arrow navigation.

## 2025-02-25 - [Ensure Keyboard Navigation Bounds Respect Disabled Elements in Customized Listboxes]
**Learning:** When implementing keyboard navigation shortcuts such as "End" and "Home" in customized composite elements (like `role="listbox"` SelectLists with mixed enabled and disabled/header/separator elements), hardcoding bounds selection (like selecting `this.rows.length - 1` directly) can lead to active keyboard focus getting trapped on disabled, non-interactive elements. To prevent this, bounds navigation must programmatically search for and stop at the first/last enabled elements, bypassing non-selectable headers and separators.
**Action:** Always search from the list boundaries dynamically for the nearest enabled element when handling "Home"/"End" actions in lists with disabled items.

## 2025-03-01 - [Interactive Audio Feedback and Seamless Pointer-to-Keyboard Focus Handoff]
**Learning:** In highly customized DOM overlays, settings adjustments (like volume range sliders) and toggles (like unmuting) are silent, forcing users to exit the menu or engage in complex test actions to confirm their preference. Providing an immediate auditory preview cue (like a soft ping) on slide release (`change` event) or unmute allows instant verification. Furthermore, when users click an option in custom composite lists (like `SelectList`), focus can be lost from the key-handling listbox container. Programmatically restoring focus to the listbox container upon item click ensures seamless continuity from mouse clicks to keyboard arrow-key navigation.
**Action:** Always provide instant audio previews on change of volume or mute, and ensure clicking listbox options programmatically focuses the listbox container to facilitate immediate keyboard interaction.

## 2025-03-03 - [Two-Step Inline List-Row Confirmation for Destructive State Changes]
**Learning:** In lightweight custom canvas/DOM-overlay menu systems, introducing full-screen modal overlays for destructive state confirmations (such as overwriting/loading a session) can break navigation flow, require complex focus trap management, and feel visually jarring. An elegant alternative is a two-step confirmation inline within the targeted list row itself. By temporarily substituting the row text and showing an "ENTER TO CONFIRM" indicator on the first activation, we prevent accidental execution while preserving keyboard listbox navigation bounds, focus styling, and the clean HUD aesthetic.
**Action:** Implement two-step confirmation inline within existing list rows instead of full-screen modals for destructive actions in lightweight overlays, preserving menu focus and layouts.

## 2025-03-05 - [Keyboard Navigation for Overflow Containers and Settings Subordination]
**Learning:** In keyboard-driven custom DOM menus, scrollable non-interactive containers (like descriptive panels or master-detail readouts) remain inaccessible to non-mouse users unless explicitly given `tabIndex="0"` and an `aria-label`. This allows them to receive focus and be scrolled using arrow keys. Additionally, setting a master override like "Mute" should dynamically disable and visually dim subordinated volume sliders (updating `aria-disabled` and replacing numeric percentage readouts with `"MUTED"`) to avoid confusing states where the volume seems adjustable but has no effect.
**Action:** Always make scrollable static columns focusable for keyboard navigation and coordinate subordinated input states visually and programmatically with their master switches.
